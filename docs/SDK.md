# OneShotLink developer guide

OneShotLink ships an HTTP API, not a published SDK package. This guide gives copy-paste
examples in curl, TypeScript and Python using only each platform's standard library. The
served OpenAPI 3.1 document at `GET /api/v3/openapi.json` is the machine-readable contract;
[API.md](../API.md) is the human-readable one.

> **Status (2026-11-21):** six runnable examples are verified against a live stack: three
> guest happy paths plus three advanced flows (passphrase gate, file secret, owner burn with
> cookie + `Origin`). `script/test-examples.sh` boots a throwaway stack and runs all six; CI
> runs it too. There is no published SDK package. TLS on a real hostname (T-70) and the host
> Redis firewall (T-71) are
> operator-owned, so public launch is **NO-GO**. The passphrase is an access gate, not
> end-to-end encryption (D-012).

### SDK support matrix

| Surface | Runtime | Auth supported | Client source | Stability |
| --- | --- | --- | --- | --- |
| curl examples | bash 4+, curl, python3 (JSON parse only) | guest + cookie/`Origin` burn in `advanced.sh` | hand-written, stdlib only | v3 additive/native JSON; v1 frozen legacy |
| TypeScript example | Node 18+ (verified on Node 24) | guest + documented cookie pattern | hand-written, stdlib `fetch` | pinned to the served OpenAPI document |
| Python example | Python 3.9+ (verified on 3.12) | guest + documented cookie pattern | hand-written, `urllib` | pinned to the served OpenAPI document |
| SPA client | Vue 3 + TypeScript, Zod 4 | cookie sessions (same-origin) | `frontend/src/lib/api.ts` | regenerated by hand when the contract changes |

There is **no generated client today**. The decision (D-018 in `docs/DECISIONS.md`) is to keep
hand-written examples while the API is pre-1.0; generate from `/api/v3/openapi.json` (for
example with `openapi-generator` or `hey-api`) once a stable v3 consumer is committed. Any
generated client must preserve the v1/v3 distinction and the non-consuming GET preview.

Set `BASE_URL` to your instance (default `http://127.0.0.1:3000`). Run the complete
examples in [`examples/`](../examples/) after starting a local stack:

```bash
BASE_URL=http://127.0.0.1:3000 bash examples/curl/quickstart.sh
BASE_URL=http://127.0.0.1:3000 node examples/typescript/quickstart.mjs
BASE_URL=http://127.0.0.1:3000 python3 examples/python/quickstart.py
```

The `advanced.sh` / `advanced.mjs` / `advanced.py` companions cover the passphrase gate, a
binary file round-trip and an authenticated burn. They require `AUTH_MODE=simple` on the target
instance (the guest quickstarts work on a default instance); `script/test-examples.sh` starts a
temporary simple-mode stack for all six. Run everything (including a throwaway stack)
with `bash script/test-examples.sh` — this is the same command CI runs.

## 1. Discover the instance

```bash
curl -fsS "$BASE_URL/api/v3/config"
```

```json
{
  "ttl_options": [1800, 43200, 86400, 259200],
  "default_ttl": 86400,
  "auth_mode": "disabled",
  "ui_enabled": true,
  "max_secret_bytes": 1048576,
  "max_file_bytes": 524288,
  "version": "0.1.0"
}
```

Read `ttl_options` instead of hard-coding durations: a deployment may narrow the allowlist,
and any other TTL is rejected with `422 validation_error`. `max_secret_bytes` is the body
ceiling (default 1 MiB). `auth_mode` is `disabled`, `simple`, or `full` (full answers `501`).

## 2. Create a secret

```bash
curl -fsS -X POST "$BASE_URL/api/v3/guest/conceal" \
  -H 'content-type: application/json' \
  -d '{"secret":"correct horse battery staple","ttl":1800}'
```

```json
{
  "secret_key": "Hk3v9QpL2mR8sT4uW6xY1a",
  "receipt": {
    "identifier": "Hk3v9QpL2mR8sT4uW6xY1a",
    "secret_ttl": 1800,
    "passphrase_required": false,
    "kind": "text"
  },
  "links": { "secret": "/secret/Hk3v9QpL2mR8sT4uW6xY1a" }
}
```

The key is opaque (≥128 bits from a CSPRNG). The plaintext is encrypted with AES-256-GCM
under the instance `SECRET` before it is stored; never log the request body. The v1
equivalent is `POST /api/v1/share` with form fields `secret`, `ttl`, `passphrase` and a
legacy response shape — use v3 for new integrations.

## 2b. File secrets (v3)

Files travel as strict base64 inside the same JSON envelope. Read `max_file_bytes` from
`GET /api/v3/config` (512 KiB by default) before reading a file into memory.

```sh
PAYLOAD=$(base64 ./notes.bin | tr -d '\n')   # portable: works on GNU and BSD/macOS
TTL=$(curl -fsS "$BASE_URL/api/v3/config" | python3 -c 'import json,sys; print(json.load(sys.stdin)["default_ttl"])')
curl -sS -X POST "$BASE_URL/api/v3/guest/conceal" \
  -H 'content-type: application/json' \
  -d "{\"secret\":\"$PAYLOAD\",\"ttl\":$TTL,\"kind\":\"file\",\"filename\":\"notes.bin\"}"
```

```ts
export async function concealFile(baseUrl: string, ttl: number, file: File): Promise<string> {
  const bytes = new Uint8Array(await file.arrayBuffer());
  let binary = "";
  for (let i = 0; i < bytes.length; i += 0x8000) {
    binary += String.fromCharCode(...bytes.subarray(i, i + 0x8000));
  }
  const res = await fetch(`${baseUrl}/api/v3/guest/conceal`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ secret: btoa(binary), ttl, kind: "file", filename: file.name }),
  });
  if (!res.ok) throw new Error(`file conceal failed: ${res.status}`);
  const body = (await res.json()) as { links: { secret: string } };
  return new URL(body.links.secret, baseUrl).toString();
}
```

A reveal of a file returns `secret_value` as base64 with `metadata.kind === "file"` and
`metadata.filename` set. Decode before writing it to disk. The filename is metadata only —
never build a destination path from an untrusted string without sanitising it.

## 3. Preview, then reveal (the contract that matters)

`GET` is a **preview**. It returns metadata only and never consumes the secret, so chat
clients and link scanners cannot destroy it:

```bash
curl -fsS "$BASE_URL/api/v3/guest/secret/$KEY"
# {"passphrase_required":false,"metadata":{"kind":"text","filename":null,
#  "created_at":1762819200,"ttl":1800}}
```

`POST …/reveal` is the **only consuming route**:

```bash
curl -fsS -X POST "$BASE_URL/api/v3/guest/secret/$KEY/reveal" \
  -H 'content-type: application/json' -d '{}'
# {"secret_value":"correct horse battery staple","metadata":{...}}

curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  "$BASE_URL/api/v3/guest/secret/$KEY/reveal" -H 'content-type: application/json' -d '{}'
# 404
```

Exactly one concurrent reveal wins: the consume is an atomic Redis compare-and-delete of
the exact serialized record, and there is an 8-way race spec proving one `200` and seven
`404`s. A preview never decrypts, so a rotated `SECRET` turns a reveal into an error without
destroying the record. Do **not** use v1 `GET /api/v1/secret/:key` from automation: that
frozen legacy route consumes.

## 4. Passphrase-protected secrets

A passphrase is an extra **access gate**, not a second encryption key: the server holds the
instance key and can decrypt. Do not describe this as zero-knowledge (decision D-012).

```bash
# create: 8–256 bytes; absent/empty means no passphrase
curl -fsS -X POST "$BASE_URL/api/v3/guest/conceal" -H 'content-type: application/json' \
  -d '{"secret":"api key","ttl":1800,"passphrase":"correct horse"}'

curl -fsS "$BASE_URL/api/v3/guest/secret/$KEY"
# {"passphrase_required":true,"metadata":{...}}   -- no content

curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  "$BASE_URL/api/v3/guest/secret/$KEY/reveal" -H 'content-type: application/json' -d '{}'
# 401, code "passphrase_required"; secret NOT consumed

curl -sS -w '\n%{http_code}\n' -X POST "$BASE_URL/api/v3/guest/secret/$KEY/reveal" \
  -H 'content-type: application/json' -d '{"passphrase":"wrong"}'
# 401, code "invalid_passphrase"; secret NOT consumed. (-f would hide the body.)

curl -fsS -X POST "$BASE_URL/api/v3/guest/secret/$KEY/reveal" \
  -H 'content-type: application/json' -d '{"passphrase":"correct horse"}'
# 200 with the value
```

A passphrase shorter than 8 bytes is rejected at create time with `422` and nothing is
written. Pre-existing records created before that floor still reveal with their original
passphrase.

## 4b. Incoming secret requests (simple mode)

An owner creates a public link with `POST /api/v3/requests` (`{"label":"…","ttl":1800}`) and
gets a `request_key` plus `links.request` (`/request/<key>`). Anyone with that link can call
`GET /api/v3/requests/:key` for a valueless preview and `POST …/respond` with
`{"secret":"…"}` exactly once. The owner sees it in `GET /api/v3/requests` and calls
`POST /api/v3/requests/:key/reveal` once to read it.

```sh
# Owner (session cookie + same-origin proof from a browser)
curl -sS -X POST http://localhost:3000/api/v3/requests \
  -H 'content-type: application/json' -H "Origin: http://localhost:3000" \
  -b cookies.txt -d '{"label":"API key please","ttl":1800}'

# Responder (public)
curl -sS -X POST http://localhost:3000/api/v3/requests/<key>/respond \
  -H 'content-type: application/json' -d '{"secret":"the answer"}'

# Owner reveals once
curl -sS -X POST http://localhost:3000/api/v3/requests/<key>/reveal \
  -H 'content-type: application/json' -H "Origin: http://localhost:3000" \
  -b cookies.txt -d '{}'
```

A second response is `409 conflict`; a second reveal is `404 not_found`. The answer is
encrypted with AES-256-GCM before storage and is text-only with no passphrase — use an
ordinary secret link when a passphrase is needed. `GET …/:key` never returns the answer, so
chat previews cannot burn it.

## 4c. Webhooks (simple mode)

Register an endpoint with `POST /api/v3/webhooks` using an array of event names. The response
contains a `signing_secret` **once**; store it in your secret manager. Listings never include
it. Events are `secret.created`, `secret.revealed`, `request.created`, `request.responded`
and `request.revealed`, and their payloads contain metadata only — never secret values.

```sh
curl -sS -X POST http://localhost:3000/api/v3/webhooks \
  -H 'content-type: application/json' -H "Origin: http://localhost:3000" \
  -b cookies.txt -d '{"url":"https://hooks.example.com/ots","events":["secret.revealed"]}'
```

Deliveries happen outside the request cycle: run `bin/ots webhooks:work` (or with a limit)
from the container. Verify the `X-OneShotLink-Signature` header by computing
`HMAC-SHA256(signing_secret, raw_request_body)` and comparing it in constant time to the
`sha256=<hex>` value. Deduplicate on `X-OneShotLink-Delivery`: that id is stable per event and
never delivered twice. Respond with any 2xx to stop retries; failures are retried up to three
times with backoff.

A minimal verifier (constant-time compare, header prefix stripped, delivery id de-duped):

```python
import hmac, hashlib

def verify(raw_body: bytes, signature: str, delivery_id: str, signing_secret: str, seen: set) -> bool:
    expected = "sha256=" + hmac.new(signing_secret.encode(), raw_body, hashlib.sha256).hexdigest()
    if delivery_id in seen or not hmac.compare_digest(signature, expected):
        return False
    seen.add(delivery_id)
    return True
```

```ts
import { createHmac, timingSafeEqual } from "node:crypto";

function verify(raw: Buffer, sig: string, id: string, secret: string, seen: Set<string>): boolean {
  const expected = Buffer.from("sha256=" + createHmac("sha256", secret).update(raw).digest("hex"));
  const actual = Buffer.from(sig);
  if (seen.has(id) || actual.length !== expected.length || !timingSafeEqual(actual, expected)) return false;
  seen.add(id);
  return true;
}
```

For a local receiver the operator must set `WEBHOOK_ALLOW_PRIVATE=true`; production endpoints
must be public HTTPS. The signature covers the **raw** body — verify before JSON parsing.

## 5. Errors, limits and retries

Every v3 error has the same envelope; keep `request_id` when reporting a problem:

```json
{"error":{"code":"rate_limited","message":"Too many requests. Slow down and try again shortly.","request_id":"…"}}
```

Message text is illustrative, not contractual — branch on `code` and `request_id`, never on prose.

| Code | HTTP | Meaning for a client |
| --- | --- | --- |
| `validation_error` | 422 | Bad TTL, empty/oversized secret, bad passphrase length — fix the request |
| `not_found` | 404 | Unknown, expired or already-consumed — do not retry |
| `passphrase_required` / `invalid_passphrase` | 401 | Supply / correct the passphrase; the record is intact |
| `rate_limited` | 429 | Back off for `Retry-After` seconds |
| `payload_too_large` | 413 | Secret value over `max_secret_bytes` (the read cap allows 16 KiB of JSON overhead) |
| `service_unavailable` | 503 | Redis down or full; retry after `Retry-After` |
| `internal_error` | 500 | Server fault; report with `request_id` |

The full scope/default table lives in [API.md §1](../API.md#rate-limits); in short: 30
conceals, 60 reveals, 10 sign-ins and 10 sign-ups per 60-second window, keyed per client
identity. A protected secret additionally has a **per-secret** budget of 5 guesses per 900
seconds (D-012b), keyed by the secret id — exhausting it does not consume the record.
`TRUSTED_PROXIES` controls whether `X-Forwarded-For` is honored. A full datastore answers
`503 service_unavailable` (also with `Retry-After`) rather than dropping secrets.

**A transport timeout is not a "did not happen".** If a `POST …/reveal` or
`DELETE /api/v3/secret/:key` times out after the server committed, the value is already gone
and a blind retry returns `404`. A timed-out `POST …/respond` is different: the answer was
stored and a second submission returns `409 conflict` (the value is retained). There is no
`Idempotency-Key` header in v1. On a timeout, re-`GET` the link or request preview to observe
the new state; only retry the write when the preview proves it was not applied. Conceal is also non-idempotent — each retry
creates another secret and another link.

Retry only `429` and `503`, honour `Retry-After`, cap the delay and the number of attempts,
and **never** retry `404`, `422`, `401 passphrase_required` or a successful one-shot reveal:

```python
import time, urllib.request, urllib.error

def get_json(url):
    for attempt in range(4):
        try:
            with urllib.request.urlopen(url, timeout=10) as r:
                return r.read()
        except urllib.error.HTTPError as e:
            if e.code not in (429, 503) or attempt == 3:
                raise
            time.sleep(min(int(e.headers.get("Retry-After", "5")), 60))
```

The examples in §7 do not implement retries; they are deliberately minimal happy paths.

## 6. Accounts (simple mode only)

When `auth_mode` is `simple`, sessions are opaque cookies (`HttpOnly`, `SameSite=Lax`,
`Secure` when the site runs under TLS). Sign-up and sign-in have **separate** rate-limit
buckets (`RATE_LIMIT_SIGNUP` and `RATE_LIMIT_SIGNIN`, each default 10 per minute); duplicate
emails return `409 email_taken`; failures are always generic `401 invalid_credentials`.

```bash
curl -fsS -c cookies.txt -X POST "$BASE_URL/api/v3/signup" -H 'content-type: application/json' \
  -d '{"email":"dev@example.com","password":"a long unique password"}'
curl -fsS -b cookies.txt "$BASE_URL/api/v3/account/me"
curl -fsS -b cookies.txt "$BASE_URL/api/v3/account/receipts"
curl -fsS -b cookies.txt -X POST "$BASE_URL/api/v3/signout" \
  -H 'content-type: application/json' -H "Origin: $BASE_URL" -d '{}'
```

Cookie-authenticated mutations require a same-origin proof (`Origin` matching the
configured `HOST` scheme/host/port, or `Sec-Fetch-Site: same-origin`). The signout example
above **must** send that header: once the request carries `ots_session`, the CSRF check is
enforced. Plain headerless API clients without a cookie are allowed. With `AUTH_MODE=disabled` account routes return `403`; with `full`
they return `501` — never silently fall back.

Concealing while signed in attaches an owner receipt. Revealing **consumes the payload but
keeps the receipt** for 30 days with `status` set to `revealed`; `DELETE /api/v3/secret/:key`
burns an unrevealed link (`200 {"ok":true,"metadata":{"identifier":"…","status":"burned"}}`,
then the link is `404`). Receipts show metadata, status and a link — never the plaintext.

## 8. Security notes for integrators

- Never put the secret in a URL, query string, log, or analytics event. Only the opaque key
  belongs in a link.
- Keep the instance `SECRET` out of source control; rotate with `bin/ots rotate-key`.
- Treat backups as sensitive: they contain ciphertext plus passphrase hashes and session
  digests.
- `GET` is safe for link previews; `POST …/reveal` spends the secret. v1 `GET` is the
  documented exception.
- The passphrase is not a second key; server-side compromise is a real threat (D-012).

## 9. SDK implementer's checklist

A compatible client must:

1. Create with `POST /api/v3/guest/conceal` and read `ttl_options` / `max_secret_bytes` /
   `max_file_bytes` from `/api/v3/config` instead of hard-coding them.
2. Treat `GET /api/v3/guest/secret/:key` as a **non-consuming** preview, and spend the secret
   only with `POST …/reveal`. Never use the frozen v1 `GET` from automation — it consumes.
3. Send `Content-Type: application/json` on v3 bodies and preserve `credentials: same-origin`
   in browsers; cookie-authenticated mutations additionally need a same-origin `Origin` or
   `Sec-Fetch-Site` proof.
4. Handle `429` / `503` using `Retry-After`, and keep the per-secret passphrase budget in mind
   when guiding users through retries.
5. Capture `X-Request-Id` from every response (success or error) and surface it in support
   reports; it is the log correlation key.
6. Constrain generated types to the served OpenAPI document at `/api/v3/openapi.json`; v1
   shapes are frozen and v3 is native JSON. Never silently fall back between API versions.
7. Never auto-retry a consuming write after a transport timeout: re-preview first. Conceal and
   respond are non-idempotent (a retry creates another link or returns `409`).
8. Clear revealed plaintext from memory as soon as the caller has copied or downloaded it.
