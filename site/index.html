The problem is not the encryption

The tool everyone reaches for is somebody else's server, and the person sending the password has no way to check what that server does with it. The usual answer is "trust us": a network diagram and a promise.

There is a second trap that catches people later. Paste a one-time link into a chat app and the preview may open it for you — and a one-time link that has been opened once is gone before your colleague ever clicks.

How it works

  1. Paste the secret. Pick an expiry, and add a passphrase if you want an extra access check.
  2. Send the link. The recipient opens it and confirms. Nothing is consumed before that.
  3. It is gone. One view, or the expiry you chose — the record is deleted from Redis. 
export SECRET="$(openssl rand -hex 32)"
export REDIS_PASSWORD="$(openssl rand -hex 24)"
docker compose up -d --build
curl -fsS http://localhost:3000/health

Then put a TLS proxy in front of it and run script/preflight.sh. The script refuses to call a deployment ready if the certificate, HSTS header, cookie flags or Redis isolation are wrong.

What it does differently

Each row is a property of the code in this repository, not a roadmap item.
Property What it means here
A host you can prove Two environment variables and one compose command. The crypto is about 60 lines and named for what it is, so you can read it before you trust it.
The share link does not spend the secret Opening the link shows a button, not the secret. Nothing is consumed until the recipient confirms, so a link preview does not burn it.
Honest crypto, stated plainly AES-256-GCM at rest under a key derived from the instance secret, verified with an authentication tag on decrypt. The server holds that key, so it can read a revealed secret; the passphrase is an access check, not a second key.
No account on either end Guests create and reveal. Accounts are optional, for receipts and a dashboard.
A single answer for every miss Expired, already opened, or never existed all return the same 404. The server does not leak which one it was.
One reveal wins The consume is an atomic compare-and-delete in Lua: eight concurrent reveals produce exactly one winner.
Nothing useful in the logs One line per request with no body, no query string, no cookies, no IP, and the secret key redacted.

Questions people actually ask

Can the server read my secret?
Yes, once it is revealed. The key is derived from the instance secret, which lives on the server. The passphrase is an extra access check, not a second encryption key, and we do not call this zero-knowledge because it is not. If the server must not be able to read it, the answer is to run the server yourself — that is the whole argument.
Will a chat preview burn my link?
Not the share link: it renders a confirmation button and consumes nothing until the recipient presses it. A direct GET /api/v3/guest/secret/:key does consume, so treat the API as a reveal and not as a status check.
Do I need an account?
No, on either end. Accounts add receipts and a dashboard, and stay optional.
How long does a secret live?
You choose from a fixed set of expiries when you create it, and Redis enforces the TTL itself, so there is no cleanup job to fail silently.
Can I import from my old tool?
No. Secrets are ephemeral by design; a bulk import would be a plaintext store, which is the thing this exists to avoid.
Does it support SSO or teams?
Not yet. The full auth mode answers 501 on purpose instead of falling back to something weaker.
Is it audited?
No. There has been no third-party security audit. What exists is a threat model in the repository, 104 specs including the at-rest ciphertext check and the wrong-passphrase-does-not-consume case, and a load test that races eight reveals per secret.

One command, two environment variables, your own Redis.
